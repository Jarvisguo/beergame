# 啤酒分销游戏模拟器

这是一个基于 Node.js、Express 和 Socket.IO 的实时网页版 Beer Distribution Game。项目用于课堂或培训场景，支持多个 4 人小组同时进行供应链运营模拟，并在管理端查看小组状态、趋势图和经营报告。

当前版本已经升级到 Socket.IO 4.x，默认游戏总轮次为 26 周。

## 功能概览

- 玩家端：4 个角色组成一队，分别为零售商、批发商、区域仓库、工厂。
- 玩家页面顶部显示从 1 开始的小组号，与管理端一致；登录、重连和小组重新编号时自动更新。
- 管理端：选择客户需求趋势、开始游戏、查看在线人数、小组成员、总库存、总积压、待下单角色和趋势图。
- 经营报告：从管理端打开，仅汇总完成全部 26 周的小组的成本、库存、积压、订单波动和牛鞭效应指标。
- 手机断线容忍：玩家手机切后台或锁屏导致 Socket 断开时，默认保留座位 10 分钟。
- 同用户名恢复：玩家在宽限期内用同一用户名重新登录，会恢复原小组、座位、角色、当前进度和已提交的订单；切回页面或断线重连无需刷新。
- 防抢座：不同用户名不能占用暂离玩家的座位。

## 技术栈

- Node.js 18
- Express 4
- Socket.IO 4
- Bootstrap 3
- 原生 HTML/CSS/JavaScript

项目数据保存在服务端内存中。重启服务会清空当前游戏状态。

## 本地运行

```bash
npm install
npm start
```

默认监听端口为 `3000`，访问：

- 玩家入口：`http://localhost:3000/`
- 管理入口：`http://localhost:3000/admin.html`
- 经营报告：管理端点击“生成报告”，或访问 `http://localhost:3000/report.html`

## 环境变量

可以参考 `.env.example`：

```bash
ADMIN_PASSWORD=change-me
MOBILE_RECONNECT_GRACE_MS=600000
```

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | 服务监听端口，Zeabur 通常会自动注入。 |
| `ADMIN_PASSWORD` | `admin` | 管理员登录密码。生产部署必须修改。 |
| `MOBILE_RECONNECT_GRACE_MS` | `600000` | 玩家断线后保留座位的宽限期，单位毫秒。默认 10 分钟。 |

## Zeabur 部署

1. 将代码推送到 GitHub。
2. 在 Zeabur 新建服务，选择该 GitHub 仓库。
3. 运行命令使用项目默认脚本：
   - Install Command: `npm install`
   - Start Command: `npm start`
4. 在 Zeabur 环境变量中至少设置：
   - `ADMIN_PASSWORD`: 管理员密码
   - `MOBILE_RECONNECT_GRACE_MS`: `600000`
5. 部署完成后打开 Zeabur 分配的域名：
   - 玩家访问根路径 `/`
   - 管理员访问 `/admin.html`

不要在生产环境继续使用默认管理员密码 `admin`。

管理员操作要求当前 Socket.IO 连接已通过密码验证。断线重连后，管理页会回到登录框，需要重新输入密码；玩家重连规则不变。未登录调用管理事件时，如提供回调，会收到 `{ err: '需要管理员登录。' }`，不会改变游戏状态。部署时应同时更新服务端与静态页面，无需迁移数据；若回滚到未包含此校验的版本，应先关闭公网访问。

玩家登录及重连的 `submit username` 成功回调新增 `groupNumber`（从 1 开始），原有字段保持兼容。玩家页用它显示小组号，并沿用 `change group subscription` 的从 0 开始的索引更新编号。缺少该字段的旧服务端只会让小组号隐藏；生效需更新服务端与玩家静态页面，无数据迁移。回滚本项会恢复为不显示小组号。

## 游戏流程

1. 玩家打开根路径并输入唯一用户名。
2. 系统按顺序分配角色：零售商、批发商、区域仓库、工厂。
3. 每满 4 人组成一个小组。所有小组都满员后，管理员选择客户需求趋势并开始游戏。
4. 每一周玩家根据自己的库存、积压、收货和下游订单决定向上游下单数量。
5. 同一小组 4 个角色都提交订单后，该小组自动进入下一周。
6. 游戏默认运营 26 周。第 26 周仍可提交订单，完成后停止继续下单。
7. 管理员可以在管理端查看看板、趋势图，并生成经营报告。

## 需求趋势与 Lead Time

管理员开始游戏前可以选择客户需求趋势：

| 趋势 | 26 周客户需求 |
| --- | --- |
| 混合趋势 | 第 1-4 周：4，第 5-8 周：6，第 9-12 周：8，第 13-16 周：10，第 17-20 周：8，第 21-24 周：6，第 25-26 周：4 |
| 增长趋势 | 第 1-4 周：4，第 5-8 周：6，第 9-12 周：8，第 13-16 周：10，第 17-20 周：12，第 21-24 周：14，第 25-26 周：16 |
| 下降趋势 | 第 1-4 周：16，第 5-8 周：14，第 9-12 周：12，第 13-16 周：10，第 17-20 周：8，第 21-24 周：6，第 25-26 周：4 |

游戏中的延迟规则：

- 订单 Lead Time：你本周向上游下的订单，上游会在下一周收到。
- 到货 Lead Time：上游本周发出的货物，会在约 2 周后到达你这里。

## 手机断线与重连

移动端浏览器切后台、锁屏或网络切换时，Socket.IO 可能触发断开。服务端不会立即移除玩家，而是进入暂离状态：

- 默认 10 分钟内，同用户名重新登录会恢复原座位和角色。
- 暂离玩家仍占用座位，其他用户名不能抢占。
- 暂离期间管理员看板保留该玩家状态。
- 超过宽限期仍未重连，玩家会被标记离线、在线人数减少，座位释放；此后不能保证同用户名恢复原位。
- 登录恢复请求 8 秒超时，临时失败会有限重试；仍未恢复时可点击“重新连接并恢复游戏”或再次登录。网络连通但玩家身份尚未恢复时显示“正在恢复游戏”，恢复成功后才显示在线。
- 同一连接、同一用户名重复登录会返回最新状态，不重复分配座位；不同连接不能抢占仍在线的同名玩家。
- 管理员移除玩家、重置游戏或服务重启会清除对应状态，不属于断线恢复保证范围。

如需调整宽限期，在 Zeabur 设置 `MOBILE_RECONNECT_GRACE_MS`。已有环境变量会覆盖代码默认值；将旧部署升级为 10 分钟时，也须将该变量改为 `600000`。本地 `.env.example` 仅是配置示例，不会自动改变 Zeabur 设置。

本次登录修复保留成功回调字段及跨连接重名错误的兼容性；同一连接切换用户名会明确返回 `{ err: ... }`。发布时应同时更新服务端和玩家页面，无数据迁移。回滚会恢复旧重连行为；宽限期仍由环境变量决定。

## 经营报告统计范围

仅完成全部 26 周结算的小组参与报告：服务端的 `week > 26` 才代表完成，正在第 26 周下单的小组仍不纳入。汇总人数、成本、牛鞭指标、排名、图表及玩家明细使用同一筛选结果，并保留管理端的原小组号。没有已完成小组时显示空状态；重置或清除数据后清空旧排名及指标。管理看板仍保留所有小组，报告筛选不删除游戏数据。管理端结束游戏时仅调整排名显示顺序，报告缓存始终保留服务端的原小组顺序，避免排名改变组号。

## 牛鞭效应指标

玩家端、管理端和报告共用 `public/bullwhip.js`：B = 订货方差 / 实际收到的新增需求方差。统计已结算的第 1—N 周，满 5 周后分档；零售商以客户需求为基准，其余角色以当周收到的下游订单为基准，考虑 1 周订单提前期，不重复计入积压。

| 倍数 | 课堂展示等级 |
| --- | --- |
| 0 ≤ B ≤ 1 | 未放大 |
| 1 < B ≤ 2 | 轻度放大 |
| 2 < B ≤ 4 | 中度放大 |
| 4 < B ≤ 8 | 高度放大 |
| B > 8 | 极高放大 |

这些是本游戏展示分档，不是行业标准；数值不封顶，按原始倍数分档。CV 仅作为订货相对波动的辅助值。需求恒定、样本不足和缺失数据分别提示，不转换成零分。一直不订货另有提示，不能用低倍数代替成本和积压评价。

新记录 `demandHistory` 保存每周实际收到的新需求；`historyStartWeek` 标明历史起始周，两个字段与 `orderHistory` 对齐。重连和接替保留原记录；重新创建角色从实际进入周起记，不虚构之前的数据。新 `next turn.analytics` 向本组玩家同步各角色的三项历史字段，使队友指标按周更新；既有字段不变。

报告只分析完成 26 周的小组，展示本环节倍数、相对最终客户需求的倍数、需求/订货曲线和累计指标趋势。小组最大值只使用可计算角色，并展示覆盖范围和恒定需求警示。缺少新字段的旧缓存保留经营总数，但牛鞭指标显示数据不完整；不猜测或补零。每周成本使用结算前成本的相邻差值和最终总成本，缺失值显示“—”。

发布时同时更新服务端和三个页面；旧客户端会忽略新增事件字段，新客户端遇到旧数据会显示不可计算。无数据库迁移。当前内存游戏无法跨服务重启保留，应在课堂结束后发布。回滚可恢复旧版本代码，但会重新使用旧指标口径。方案、批准和本地验证记录见 [指标实施记录](docs/jarvispowers/bullwhip-metrics.md)。

## 维护说明

- 当前游戏轮次上限在服务端和前端均为 26 周。
- 管理端报告数据来自当前服务端内存状态，不是持久化报表。
- 修改游戏计算逻辑后，应同步更新 `tests/integration/five-week-operations.test.js` 中的期望值。
- 修改 Socket.IO 行为后，应运行完整 `npm test`，避免移动端重连和断线宽限逻辑回归。
